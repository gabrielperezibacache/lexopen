# Revisión PR #202 — roles, muro ético y tareas unificadas

Fecha: 2026-11-01. Head revisado: `0193d410a5c5aa4d59c13432227ef9886c35c153`. Main de comparación: `72400f9b9627cdc147ebf7c14a791c063747a686`.

**Decisión recomendada: solicitar cambios; no integrar todavía.** Revisión del árbol completo de #202 y comparación directa con main. No se modificó código ni se usaron credenciales/datos reales. Los hallazgos son de flujo verificable en fuente; la comprobación del matcher usa la implementación real de Next instalada, sin HTTP/DB.

## Bloqueantes

1. **P1 — el muro ético no cubre las vías alternativas de lectura.** `src/app/api/documentos/[id]/content/route.ts:11-23` pide staff y verifica solamente los flags de confidencialidad; `canReadFlagged` (`src/lib/api.ts:126-133`) no consulta causa/equipo. Un usuario excluido de una causa `acceso=equipo` puede obtener su documento no marcado mediante ID. La búsqueda revela documento y causa en `src/app/api/search/route.ts:261-283` sin `causaAccessWhere`; las tareas tampoco se acotan en 285-296. También revisar cliente→causas, movimientos/PJUD, minutas, archivos y contexto del asistente: introducir el muro solo en la ficha de causa no aísla el expediente. Cierre: filtro compartido por relación de causa en todas las listas y comprobación antes de lectura/descarga/mutación; pruebas negativas directas y vía búsqueda/IA/exportaciones.

2. **P1 — 2FA obligatorio se evade con encabezados prefetch.** La política se evalúa solo en `src/proxy.ts:303-307`; el matcher `src/proxy.ts:357-364` excluye requests que contengan `next-router-prefetch` o `purpose: prefetch`. `requireUser` (`src/lib/auth/session.ts:89-96`) no verifica enrolamiento. Un admin autenticado sin TOTP puede solicitar la API con `purpose: prefetch` y alcanzar los handlers protegidos únicamente por sesión/rol. Se ejecutó `next/experimental/testing/server` (export real instalado `unstable_doesMiddlewareMatch`): `/api/causas` sin header→true, con next-router-prefetch:1→false, con purpose:prefetch→false. Es prueba del matcher; falta E2E HTTP. Cierre: aplicar política también al control servidor, o asegurar matcher de APIs sin exclusión y mantener defensa en profundidad. `two-factor-policy.ts:17-18` también permite `LEXOPEN_E2E=1` sin excluir NODE_ENV=production; no usar esta configuración como prueba de seguridad real.

3. **P1 — lectura no equivale a permiso de escritura.** `src/app/api/causas/[id]/route.ts:71-74` solo requiere staff y `assertCausaAccess`, que verifica lectura. La matriz (`src/lib/auth/permissions.ts:66-68`) niega `causa.write` y `causa.create` a contabilidad; pese a ello una cuenta de contabilidad miembro puede editar datos/reasignar responsable. Los revokes de escritura tampoco se aplican. Cierre: exigir capacidad de operación con el rol de membresía; nunca usar `canSome` como autorización final para permisos scoped. Revisar todos los handlers históricos que dependen de `requireStaff` al agregar estos roles.

4. **P1 — PATCH masivo de tareas omite las nuevas restricciones.** `src/app/api/tasks/route.ts:181-193` ejecuta updateMany por IDs; no verifica muro, permiso de reasignación/delegación, historial ni transiciones. El PATCH individual (`200-243`) tampoco comprueba acceso a la causa actual o destino. Una cuenta staff puede alterar tareas conocidas de otra causa y el bulk permite eludir el control de reasignación individual. Cierre: resolver y autorizar cada recurso, acotar updateMany por causas accesibles y validar capacidad; transacción con historial, estado completado y espejo; rechazo sin escrituras parciales de lotes mixtos.

## Seguimientos funcionales

- **P2 — espejo unilateral.** `src/lib/tasks/sync-mirrors.ts:29-108` solo implementa TaskFromTramite / TaskFromMinutaAccion. `src/app/api/tasks/route.ts:221-360` no refleja completar/reasignar de Task en el trámite o acción original. Completar la bandeja deja abierto el checklist; una edición posterior del trámite puede reabrir su Task. Definir fuente única o sincronización transaccional bidireccional, evitando bucles y carreras.
- **P2 — aprobación no aplica decisión de negocio y no controla expiración/concurrencia.** `src/lib/auth/aprobacion.ts:82-130` lee estado y actualiza por ID sin condición estado=pendiente, no consulta venceAt ni aplica efecto a entidad. Dos resoluciones compiten; una aprobación expirada se admite. Debe ser una máquina de estados con compare-and-set, auditoría atómica y efecto explícito o estado claramente informativo.
- **Cobertura insuficiente para autorización:** `e2e/roles-ethical-wall.spec.ts` solo comprueba opciones de roles y encabezado de tareas. Los tests de funciones puras no certifican cierre del muro en handlers ni 2FA obligatorio porque la suite relaja enrolamiento. Exigir matriz real rol×recurso×membresía×grant/revoke en API y navegación; escenarios de concurrencia para mirrors/aprobaciones.
